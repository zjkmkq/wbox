# 五步专家模式

## ① 拆（extract）

**做什么**：apktool 解包 → 资源清单 → 模块骨架 → 行为骨架 → 写入 `spec.json`。

**判形态**（这一步现在会先跑）：
- `assets/public/index.html` 或 `assets/www/index.html` 存在 → H5 壳，框架类一律弃
- `lib/**/libgdx.so` → libGDX 原生，准备提炼数值
- `lib/**/libunity.so` → Unity，**先停下来讨论要不要接**
- `res/layout/*.xml` → 常规原生，逐页重建

**产出**：资源条目（路径、类型、大小）、模块（Activity/Service/组件）、行为（入口、关键类）。

**什么时候往下走**：资源清单里"自有 vs 库"已经分清了。分不清就往下走，后面每一步都会被库资源淹没。

> 实测教训：跳石子工程一开始 134 个 Capacitor 框架类被当成业务类进了工程，装配器还把它们注册成 7 个页面，HAP 反而更大更慢。

## ② 画拼图（plan）

**做什么**：生成提案——每个资源/模块给"迁移 / 弃 / 待裁决"，并推测逻辑类与 UI 单元。

**要看什么**：
- 提案里 `迁移` 的对象是不是你认得的业务资产
- `逻辑类` 里有没有 `Bridge`、`Plugin`、`JSObject`、`$$ExternalSyntheticLambda` 这类框架噪音（有就说明形态判错了，回去改）
- `待裁决` 的数量。超过 20 条说明拆得不够干净

**产出**：可编辑的提案表（这是你的判断的起点，不是结论）。

## ③ 判断（decide）

**做什么**：逐条确认或推翻提案，写进 `decisions`。

**规则**：
- `decided_by` 永远是 `human`，AI 只提案不决定
- 每条决定要给理由（"库资源，无对应"比"弃"有用得多）
- 拿不准的标"待裁决"，不要瞎猜——瞎猜的决定会在第⑤步变成缝

## ④ 填上（fill）

**做什么**：把 AI 生成的 ArkTS 草案落地。三条通道：
1. 导出任务包（`exports/ai_output.md`）→ 你去对话式 AI 拿结果 → 粘回来
2. API 直连（配了 key 的话）
3. 粘贴导入

**交付物格式**（重要）：AI 要给的是**可粘贴的 FILE 块**：

```
// FILE: entry/src/main/ets/pages/Index.ets
（代码）
```

首行 `// FILE: 路径` 是元数据，导入时会被消费掉。**HAP 不是这一步的产物**，别在这里找包。

## ⑤ 装配（assemble）

**做什么**：草案 + 资源 + 鸿蒙工程骨架（`templates/harmony/`）→ 可编译工程 → hvigor 编译 → HAP。

**成功判据**：`BUILD SUCCESSFUL` + HAP 字节数。退出码非零通常是沙箱拦了 `wmic.exe`，不算失败。

**骨架必须有**（缺一个就报 00304056）：`build-profile.json5`、`hvigorfile.ts`、`hvigor/hvigor-config.json5`、`entry/build-profile.json5`、`entry/hvigorfile.ts`、`oh-package.json5` ×2、`oh-package-lock.json5`、`AppScope/` 三件、`module.json5`、`EntryAbility.ets`、`color.json`、`string.json`、`app_icon.png` ×2、`router_map.json`。

## ⑥ 补缝（seal）

**做什么**：列出所有"没做到位但先跑起来了"的地方，逐条定状态（open / verified）与关闭判据。

**这就是白盒的意义**：迁移从来不是"跑通即完成"。跑通只是让缝暴露出来。

典型缝：切割手感没调、某个弹窗没做、字体在特定设备上偏色、某个音频没播。

**每条缝必须写"怎么算关闭"**，否则它永远不会关。
