# 原生游戏迁移实战（圆锯模拟器）

## 起点

- libGDX 游戏，逻辑在 Java 里，被 R8 混淆
- 自有代码和库代码**同在顶级短包**（`w0`、`a`、`z3` 之类），看包名必错
- 13000+ 个类，真正属于游戏的只有 132 个

## 核心问题：哪些代码是我要迁的

### 判定链（三步）

1. **manifest 入口** → 只取自有的入口，库组件会带入 `androidx` 的混淆短包
2. **smali 类型引用 BFS 闭包** → 从入口出发能到达的类
3. **`_is_own_pkg(rel, own_prefix)`** → 包在 manifest 包子树里 / 是短包名 / 是 `com` 但非已知库

实测结果：**入口可达自有 132 类 / 库及不可达 8932 类**。

> 任务包里的 smali **必须按包路径落盘**。同名类平铺会互相覆盖，一覆盖就全乱。

## 第二个问题：不该翻译什么

不要翻译：
- 游戏主循环（`render(delta)` 那套）
- 任何 `GL20.*` 调用
- 场景图、材质、Shader

要提取的只有**数值和规则**：

```
切割公式：cutSpeed × woodValue × 2.5 / (level.a × level.b) × dt
8 种锯的价格与速度
3 种木头的 value
6 个关卡的 a/b 参数
视野：12.8 × 7.2
```

这些数字写进 `spec.json` 的 log 记录，是唯一可信的迁移依据。**凭感觉调出来的手感不叫迁移。**

## 第三个问题：鸿蒙侧的三个硬限制

### Canvas 没有 drawImage

`CanvasRenderingContext2D` 不提供 `drawImage`。位图必须用**声明式** `Image($rawfile('...'))` + `position` 定位。

Canvas 只负责粒子（木屑飘落之类）。

### 路径里的纯数字段不能被"拼音化"

`logs/1/1.png` 里的 `1` 是纯 ASCII，**必须原样保留**。

如果无差别调用 `ascii_name`，裸数字会触发兜底哈希：`1` → `1_c4ca`。结果所有 libGDX 路径引用错位，素材全白搬。

规则：**只对"含非 ASCII 字符"的路径段做化名**。

### 横屏

```typescript
mainWindow.setPreferredOrientation(window.Orientation.LANDSCAPE).catch(() => {})
```

`setWindowOrientation` **不存在**（API 26 上），而且这个方法返回 Promise，必须 catch。

## 第四个问题：素材语义映射

不要按原路径照搬，按语义：

```
logs/<1..6>/<1..4>.png   → 木头：等级 × 加工阶段（progress → stage）
disks/disk<1..8>.png     → 锯片
ui/bg.png                → 背景
ui/menu_title.png        → 菜单标题
particle/sawdust.png     → 木屑粒子
```

## 结果

- HAP：8,074,202 字节，BUILD SUCCESSFUL
- 3 个页面 + 3 个组件 + 3 个对话框 + 5 个逻辑类 + 96 个 rawfile
- 缝清单 6 条（5 条 verified，1 条 open：切割手感待完整玩法验收）

## 这条工程教会的事

1. **混淆工程里，包名不是线索，引用闭包才是**
2. **原生游戏的"迁移"= 提炼数值 + 重建玩法**，翻译代码是死路
3. **素材路径的 ASCII 化必须是"选择性"的**，无差别处理会毁掉引用
4. **缝要写清关闭判据**，否则"切割手感"这条缝永远开着
